# Продающая страница-лонгрид

Страница, которую человек читает сверху вниз как статью и в конце нажимает одну кнопку.
Не сетка блоков с тарифами, а текст, который ведёт.

Заполненный пример структуры лежит в `templates/content.example.py`. Данные там
ВЫДУМАНЫ, оттуда берётся только СТРУКТУРА: какие блоки, в каком порядке, какой длины.
Формулировки, кейсы, цифры, имена и обещания оттуда не переносятся никогда, у твоего
клиента своя фактура и свой голос. Копируешь для работы `templates/content.template.py`,
он пустой намеренно.

## Когда берём этот скилл

- клиент просит сайт, лендинг, продающую страницу, статью под трафик;
- есть готовый продающий текст (или его надо написать) и материалы: кейсы, отзывы, фото;
- цель страницы — одно действие: перейти в бота, написать в личку, оплатить.

Если текста ещё нет, а есть большой оффер владельца по блокам — сначала скилл
`selling-article`: он выбирает схему, пишет блоки и снимает дизайн с референса. Потом
сюда, на вёрстку и деплой.

Если нужна база знаний с гайдами — это другой скилл, `client-knowledge-base-site`.
Если нужна презентация — `present`.

## Железное правило: текст клиента переносим слово в слово

Продающий текст, который дал клиент, идёт на страницу **дословно**. Не сокращаем,
не «улучшаем», не переписываем под свой вкус. Наша работа — вёрстка, ритм, расстановка
акцентов и доказательств. Меняем текст только там, где клиент прямо попросил.

Всё, что пишем сами (подзаголовки блоков, подписи, микрокопия у кнопки), обязано
пройти правила живой речи: без длинных тире, без «не X, а Y», без канцелярита.

## Порядок работы

### 1. Собрать материалы ДО вёрстки

- продающий текст,
- кейсы (имя, ник, цифра, точка А, точка Б),
- отзывы (скриншоты переписок берём как есть, они выглядят честно),
- фото клиента (портрет в первый экран + рабочие кадры),
- ссылка, куда ведёт кнопка (бот, личка, оплата),
- реквизиты в подвал: ИП/название, ИНН, ссылки на оферту и политику.

Материалы клиента тяну сама: Яндекс.Диск через
`cloud-api.yandex.net/v1/disk/public/resources`, картинки действующего сайта через
`google-chrome --dump-dom` и вытяжку ссылок на CDN, фото из рабочего чата через
`telegram-chip`.

Если у клиента есть страница-референс, разбираю её по блокам скриншотами и показываю
разбор, прежде чем верстать. Это снимает половину правок.

### 2. Заполнить `content.py`

Весь текст живёт отдельно от вёрстки. Копирую `templates/content.template.py` в
`src/content.py` проекта и заполняю. Правки клиента идут только сюда, `build.py` не трогаю.

**Блок `META` заполняем первым.** Туда уходят title страницы, превью ссылки в Telegram,
имя автора, файлы фотографий и подписи над блоками. До 30.07 эти строки были вбиты внутрь
`build.py` литералами, поэтому любая собранная страница выходила с именем клиента ЧУЖОГО
агента: в заголовке вкладки, в превью ссылки и в alt фотографий. Теперь сборка падает и
называет незаполненные поля, пока в них стоит маркер `TODO_`. Значения снимаем с материалов
своего клиента, чужие не подставляем даже как отправную точку.

Блоки эталона, сверху вниз:

| Блок | Что делает |
|---|---|
| `HERO` | кто автор, обещание, кнопка, портрет |
| `PAIN` + `PAIN_Q` | боль дословно словами клиента, вопрос-крючок «Знакомо?» |
| `TRUTH` | разворот: с человеком всё в порядке, причина в другом |
| `PROGRAM`, `LOOPS`, `CAUSE` | механика проблемы |
| `AUTHOR` | кто ведёт и почему ему верить |
| `LEVELS`, `STEPS` | как устроено решение: уровни карточками, шаги крупными цифрами |
| `RESULTS` | что говорят те, кто прошёл |
| `CASES` | клиенты в цифрах: аватарка, ник, сумма |
| `STORIES` | истории до и после: точка А крестиками, точка Б галочками |
| отзывы | скриншоты Telegram, лента вбок |
| `FEARS` | три возражения и ответы |
| `PRICE` | сколько стоит и с чем сравнить |
| `FINAL` + `SIGN` | два пути, кнопка, подпись автора |
| `FOOTER` | реквизиты, оферта, политика |

Блок можно убрать, порядок менять не стоит: он ведёт от боли к действию.

### 3. Собрать и посмотреть глазами

```bash
python3 src/build.py                     # → out/index.html
node src/shot.mjs "file://$PWD/out/index.html" qc/desktop.png 1440 900
node src/shot.mjs "file://$PWD/out/index.html" qc/mobile.png  430 932
```

Полностраничный снимок выходит длинным, режу его на куски и смотрю **каждый**:

```python
from PIL import Image
Image.MAX_IMAGE_PIXELS = None
im = Image.open('qc/desktop.png'); w, h = im.size
for n, y in enumerate(range(0, h, 2200)):
    c = im.crop((0, y, w, min(y + 2200, h))); c.thumbnail((900, 2000))
    c.save(f'qc/desktop_{n:02d}.png')
```

Смотрю телефон отдельно и полностью. Половина дефектов вылезает только там.

### 4. Показать на согласование

Скриншоты десктоп и телефон + одним файлом сама страница
(`out/*_single_file.html`, все картинки внутри, открывается без интернета).
Одним сообщением: что внутри по блокам, что решила по ходу, что нужно от клиента.

### 5. Проверить собранную страницу перед выкладкой

Две проверки, обе обязательные, обе по СОБРАННОМУ файлу, а не по исходникам.

```bash
grep -oiE '<имя чужого клиента>|<продукт чужого клиента>' out/index.html | sort | uniq -c
grep -c 'http://' out/index.html
```

Первая ловит чужую фактуру. Гейт `META` закрывает главный путь, но имя могло приехать и
текстом: копипастой абзаца из чужого проекта, подписью к картинке, alt в ручной вставке.
Список ищем не только по своему клиенту, а по именам ВСЕХ клиентов команды, чьи страницы
собирались этим скиллом. Правило то же, что в базах знаний: наличие ключа это гипотеза,
доказательство это чтение на своём пути.

Вторая ловит адреса по http внутри страницы, которая отдаётся по https. Браузер такие
картинки и скрипты молча не грузит, а в консоли это видно только тому, кто её открыл.
Живой адрес проверяем запросом, а не глазами: `curl -sI https://<домен>/ | head -1` обязан
вернуть 200, и отдельно проверяем, что http-адрес того же домена уводит на https.

### 6. Выложить

Домен покупает и направляет клиент, это его зона и его расход. Пока домена нет,
страница живёт локально и показывается файлом со скриншотами. Как появится — деплой
как обычную статику, дальше по `reference-blog-deploy-path`.

## Гоши, на которых уже потеряли время

- Chrome `--screenshot` на странице с `min-height:100svh` снимает только первый экран.
  Нужен Playwright с `fullPage` (`scripts/shot.mjs`). Playwright берём из уже существующего
  чекаута по `$PLAYWRIGHT_PATH`, свой не ставим и файлы в чужом репозитории не оставляем.
- В полностраничном снимке `loading="lazy"` картинки остаются пустыми, а reveal по скроллу
  не срабатывает. Перед снимком принудительно `loading='eager'` и класс `.in` на `.rv`.
  В `shot.mjs` это уже зашито.
- Липкая кнопка внизу экрана попадает в полностраничный снимок дважды. Это артефакт
  скриншота, на живой странице её видно один раз. Не «чинить».
- Скриншоты для Telegram кладём в воркспейс: отправка отказывается брать файлы из `/tmp`.
- Кейсы верстаем элементами страницы, а не картинкой. Картинка не читается на телефоне
  и грузится долго.
- **Картинок в скилле нет и не будет.** `content.example.py` ссылается на 36 файлов
  (портрет, 15 аватарок кейсов, 10 скринов отзывов, аватарки историй), а лежат они в
  `out/img/` конкретного проекта. Собранная страница с пустым `out/img/` показывает рамки
  с alt-текстом — это нормальный старт, а не поломка движка. Свои картинки клиента кладём
  в `out/img/` ДО сборки, имена по схеме `case_NN.jpg`, `review_NN.jpg`, `story_NN.jpg`.
- **Липкая кнопка в полностраничном снимке видна дважды** — артефакт скриншота, на живой
  странице она одна. Не «чинить».
- **Горизонтальная лента на телефоне даёт дыру под короткой карточкой.** Высота ленты равна
  самой высокой карточке, и это не лечится `align-items`. На 430px в кадре одна история, поэтому
  под короткой зияло до 316px пустого фона. В движке решено так: на брейкпойнте ≤900px лента
  историй (`.rail.stories`) раскладывается в столбик (`display:grid`), первые три открыты,
  остальные под кнопкой «Показать ещё N историй», подпись «Листай в сторону» там прячется.
  Лента отзывов остаётся горизонтальной: скрины узкие, в кадре видно соседний, рваный низ
  читается как галерея, а столбиком это дало бы три тысячи пикселей скриншотов подряд.

- **Шрифт заголовков берём с сайта клиента, а не «похожий».** Тильда прячет гарнитуру под
  своим именем: в теме стоит `font-family:'Showshrift'`, а внутри проектного CSS
  (`static.tildacdn.com/ws/project<id>/tilda-blocks-page<id>.min.css`) видно, что весом 700
  подключён другой файл. Забираем сам `.woff` в `out/fonts/`, объявляем `@font-face` и держим
  имя в токене `--serif`, чтобы страница не зависела от Тильды. Перед сборкой проверяем
  кириллицу через fontTools (`getBestCmap`), иначе Й и Ё вылезут квадратами.
- **Антиква часто unicase**: строчные рисуются капителью, все заголовки идут капсом. Это не
  поломка, у клиента на сайте так же. Кегль и межстрочный под капс подбираем заново
  (`h2` ушёл с 1.12 на 1.17), иначе строки жмутся.
- **Ёлочки в антикве идут с широкими боковыми полями**, слово в кавычках разъезжается,
  а точка после закрывающей отлетает. Лечится классом на самих кавычках:
  `.q{margin:0 -.16em}` и `.q2{margin-right:-.3em}` на закрывающей.
- **Дефекты шрифта проверяем на полном разрешении, не по миниатюре.** Уменьшённый скриншот
  съедает бревис у Й и хвост у запятой, дважды выглядело как отсутствующий глиф. Прежде чем
  чинить, режем кроп 1:1 или смотрим метрики глифа.
- **Картинка превью ссылки набирается тем же шрифтом, что и страница.** `og:image` рисуем
  отдельной html и снимаем тем же `shot.mjs` (1200×630, `html,body{width:1200px;height:630px;
  overflow:hidden}`, иначе размер уедет). Поменяли заголовок или гарнитуру, пересобрали превью.

- **Переносы чиним в движке, а не руками.** В `build.py` есть `typo()`: неразрывные пробелы
  внутри чисел и перед валютой (иначе «10 000 ₽» на телефоне рвётся на две строки), предлоги
  и союзы не висят в конце строки, частицы «бы/же/ли» липнут к предыдущему слову. Цеплять
  подряд ВСЕ короткие слова нельзя: получается длинное неразрывное «и не пытается», которое
  на 360px вылезает за край, поэтому цепочки длиннее пары движок расклеивает сам. Плюс
  `text-wrap:balance` крупным заголовкам и `text-wrap:pretty` абзацам; мелким заголовкам в
  карточках balance вредит, они рвутся лесенкой.
- **Каждой картинке проставляем width/height при сборке** (`sizes()` читает размеры через PIL).
  Без них браузер не знает высоту кадра до загрузки файла, и страница прыгает по мере
  подгрузки. В обычном браузере это гасит кеш, а во встроенном браузере Telegram выглядит как
  тряска при первой прокрутке. Рядом обязателен `img{height:auto}`, иначе картинка растянется
  до своей настоящей высоты.
- **Под встроенный браузер Telegram** (оттуда идёт весь трафик по ссылке из бота) на
  `@media (hover:none)` снимаем закреплённый слой зерна с `mix-blend-mode` и тяжёлые `blur`:
  вебвью пересчитывает их на каждом кадре прокрутки.
- **Скриншот выше 16384px обрезается в белое.** Это предел Chrome, а не дефект страницы. Узкая
  ширина даёт более длинную страницу, поэтому на 360px хвост часто «пропадает». Проверять
  такой хвост надо живым скроллом (`scrollTo` + снимок вьюпорта), не забыв погасить
  `scroll-behavior:smooth`, иначе снимок уедет в середину.

## Что отдаём клиенту в конце

1. Страница на его домене (или файлом, пока домена нет).
2. Скриншоты десктоп и телефон.
3. `src/content.py` — файл, где он сам может поправить любой текст.

## Дизайн

Тёмный премиум: почти чёрный фон, золото акцентом, засечные заголовки (Playfair Display),
Manrope в тексте, зерно через SVG-фильтр, появление блоков по скроллу, липкая кнопка снизу.
Токены и CSS внутри `scripts/build.py`. Под другого клиента меняем палитру и шрифты там же,
структуру блоков оставляем.
